# P0 — 连接与 API 可行性的实测结论

> 本文是 [`docs/development/00-feasibility.md`](../docs/development/00-feasibility.md) 的 P0 执行版，写在 `find/`，**未修改 `docs/development/`**。
> 2026-10-23 在 DSH `0.2.1-rc.2` 上完成了第一轮实测；本文把“计划”改为“计划 + 实测结果”。
> 详细的命令、原始帧和逐项记录见 [`p0-report.md`](./p0-report.md)、[`dsh-api-inventory.md`](./dsh-api-inventory.md) 和 [`compatibility-risks.md`](./compatibility-risks.md)。

## 1. 结论先行

**P0 结论：Conditional Go。**

| 范围 | 结论 | 依据 |
|---|---|---|
| 交互式 TUI（P4） | **Go** | `/connect`、Cookie、`$events`、session/workspace、prompt/stream、history/page、approval allow/reject、cancel、断线重连、Host 重启后恢复均已实测 |
| `-p` 非交互模式 | **No-Go** | 没有 `answer` 客户端时，审批请求不会 fail closed，而是无限期悬挂；90 秒实测未结束 |
| P2 的 Node adapter | **No-Go（官方 client model）** | `@deepseek-ai/dsh-api-session-controller/client` 是浏览器 bundle，Node 导入即 `window is not defined`；`/remote` 与 `api-gateway/client` 可在 Node 加载 |
| 最小 Host 插件 | **生产必需，原型可选** | 版本/能力握手缺失；审批需要 Host 侧超时或 fail-closed 答案器；否则 `-p` 和“最后一个 answer 客户端断开”都无法安全收尾 |

一句话：**“能连、能跑、能审批、能恢复”已经成立；“非交互也安全”还不成立。**

如果产品只做交互式 TUI，P4 可以开始；如果 `-p` 是核心能力，先解决审批悬挂，再进 P4。

## 3. 已经跑通的闭环

```text
读启动 URL
  → GET /connect?token=<token>&interactions=answer
  → 302 + Set-Cookie
  → POST /api/session/list
  → WS /api/remote.mux + $events
  → ready { clientId, host: { home } }
  → session/create
  → session/follow（snapshot）
  → session/prompt
  → 事件流：turn/start … assistant/message … turn/end
  → approval/request → $events/result → approval/decided
  → session/page（历史分页）
  → 关 socket → 旧 Cookie 401
  → 同一 token 重新 /connect → 新 Cookie → 恢复
  → Host 重启 → 旧 token 401 → 新 token → session 历史仍在
```

实测中最关键的三条“非直觉”行为：

1. **`$events` 的转发事件是包在 `item` 里的**，不是顶层 `waterfall`：
   ```json
   {"type":"item","streamId":"s1","value":{"type":"waterfall","event":"approval/request","eventId":"…"}}
   ```
   如果客户端只监听顶层 `waterfall`，会完全收不到审批。
2. **`interactions=none` 不会让审批 fail closed**：`$events` 被拒绝，但 Host 的 `api-remotes` 仍然把审批放进 Remote 队列；没有 answerer 时它就等着，直到某个 `answer` 客户端出现。
3. **官方 `session-controller/client` 不是 Node 模块**：`lib/client.js` 第一行就是 `window.__ModuleLoader__.load({...})`，Node 导入直接失败。Node 侧应使用 `@deepseek-ai/dsh-api-session-controller/remote` 或自建 adapter。

## 4. 与计划的差异（重点）

| 原计划假设 | 实测 | 影响 |
|---|---|---|
| `session-controller/client` 是 React-free Client Model，可在 Node 用 | 浏览器 bundle；`window is not defined` | P2 不能直接挂它；改用 `/remote` + 自建 store，或做 Host BFF |
| `$events` 直接发 `waterfall`/`emit` | 实际是 `item.value.type = waterfall/emit/cancel` | 客户端协议层必须按 `item` 解包 |
| 没有 answerer 时审批 fail closed | 实际悬挂；`none` 客户端 90s 未结束 | `-p` 必须加 Host 侧超时/答案器，或客户端 watchdog |
| 最后一个 answer 客户端断开时 pending 会取消 | 实际保留；新 answer 客户端会再次收到同一 `eventId` | 重连要能恢复审批 UI；否则 turn 永远 running |
| `workspace.list` 存在 | 实际没有；用 `workspace/follow` 的 baseline | 列表逻辑按流式 baseline 写 |
| `session.page` 的 `maxMessages` 是记录数上限 | 实际是 message/turn 对齐的窗口；10 条消息可能返回 52 条记录 | UI 分页不要按记录数假设 |
| `$events.ready` 可能带 Host 版本 | 只有 `{ clientId, host: { home } }` | 版本诊断没有数据源；需要插件或行为探测 |
| `headless` 也能提供 API | `headless` 没有 `connection`/`session-controller`/`api-remotes` | Host 基线必须是 `web` profile，或自建 Host bundle |

### P0-1 token → `/connect` → `$events`

- [x] 从启动 URL 解析 `token`
- [x] 手动处理 302，请求 `GET /connect?token=<token>&interactions=answer`
- [x] 保存 `Set-Cookie`

实测：

```text
GET /connect?token=<token>&interactions=answer
→ 302 Found
  location: ./api/remote.mux
  set-cookie: dsh-auth-<authority-hash>=<opaque>;
              Max-Age=2592000; Path=/; HttpOnly; SameSite=Strict
```

`$events` 的 ready：

```json
{"type":"item","streamId":"s1","value":{
  "type":"ready",
  "clientId":"<uuid>",
  "host":{"home":"<home>"}
}}
```

边界：

| 请求 | 结果 |
|---|---|
| 无 Cookie `POST /api/session/list` | 401 |
| 无 Cookie `GET /api/remote.mux`（WS upgrade） | 401 |
| 无 Cookie `GET /` | 401 |
| 错误 token `/connect` | 401 |
| 旧 token（Host 重启后） | 401 |
| 旧 Cookie（socket 关闭后） | 401 |

**结论**：认证链路可用；Cookie 是 owner 凭据，必须按 root 权限处理。

### P0-2 Remote 命名空间与 Node 兼容性

Wire 层已跑通：

- [x] `session/list`
- [x] `session/create`（`cwd` 或 `workspaceId`）
- [x] `workspace/create`
- [x] `workspace/follow`（baseline + upsert）
- [x] `session/follow`

- [ ] 用官方 `session-controller/client` 在 Node 挂载
- [x] 用官方 `session-controller/remote` 在 Node 导入
- [x] 用官方 `client-connection/client` 在 Node 导入
- [x] 用官方 `api-gateway/client` 在 Node 导入

官方包导入结果：

| 入口 | Node 结果 | 说明 |
|---|---|---|
| `@deepseek-ai/dsh-client-connection/client` | OK | 有 `node` 条件导出，加载 `lib/client.node.js` |
| `@deepseek-ai/dsh-api-gateway/client` | OK | 有 `node` 条件导出 |
| `@deepseek-ai/dsh-api-session-controller/remote` | OK | 导出 `TYPERT_REMOTE` / default |
| `@deepseek-ai/dsh-api-session-controller/client` | **FAIL** | `ReferenceError: window is not defined`；文件以 `window.__ModuleLoader__.load` 开头 |
| `@deepseek-ai/dsh-client-file-upload/client` | **FAIL** | 同样是浏览器模块 bundle |

**结论**：P0-2 只能算 **部分通过**。协议/Remote 可用，但“官方 Client Model 直接跑在 Node”不成立。P2 的方向应是：

```text
@deepseek-ai/dsh-api-gateway/client
  + @deepseek-ai/dsh-api-session-controller/remote
  + 自己的 store / projection / reconnect
```

而不是：

```text
@deepseek-ai/dsh-api-session-controller/client   ← 浏览器 bundle，Node 不可用
```

```text
system/message
user/message
```


**结论**：通过。prompt、流式、工具调用、取消都能工作。

### P0-4 历史与分页

- [x] `session/page` 拉一页历史
- [x] `beforeSeq` 再拉一页
- [x] 断线后重新 `session/follow`，snapshot 一致
- [x] Host 重启后历史仍在

实测：

```text
throughSeq=79, maxMessages=10
→ records=52, seqs=28..79, hasMore=true

throughSeq=79, beforeSeq=28, maxMessages=10
→ records=28, seqs=0..27, hasMore=false, overlap=[]
```

注意：

- `maxMessages` 不是记录数上限；它是**消息/turn 对齐**的窗口，记录数可以远大于 10。
- `throughSeq` 必须 ≤ 当前 cursor；传 `cursor + 1` 会得到
  `gateway/bad-request: session page through seq … is past cursor …`。

**结论**：通过；分页语义需要在 P2 的 store 里按 message/turn 处理，不能按记录数切。

### P0-5 审批与多客户端

- [x] 触发需要审批的 bash 动作（sandbox escalation）
- [x] 收到 `approval/request`，含 tool/callId/reason/displayReason
- [x] 提交 `allowed-once`，工具继续
- [x] 提交 `rejected`，工具失败关闭
- [x] 两个 `answer` 客户端收到同一请求；一个先答，另一个收到 cancel
- [x] `interactions=none` 收不到审批
- [!] 没有 answerer 时 fail closed

审批请求实际形状（包在 `$events` 的 `item` 里）：

```json
{
  "type": "item",
  "streamId": "s1",
  "value": {
    "type": "waterfall",
    "event": "approval/request",
    "eventId": "<uuid>",
    "agentId": "session-<uuid>",
    "request": {
      "toolName": "bash",
      "callId": "call_<id>",
      "reason": "escalate sandbox to danger-full-access: …",
      "displayReason": {
        "en": "Allow this operation with danger-full-access permissions: …",
        "zh": "允许本次操作使用 danger-full-access 权限：…"
      }
    }
  }
}
```

应答：

```http
POST /api/$events/result
Content-Type: application/json
Cookie: dsh-auth-<authority-hash>=<opaque>

{
  "type": "client-request",
  "rpcId": "<uuid>",
  "method": "$events/result",
  "payload": {
    "args": {
      "clientId": "<clientId>",
      "eventId": "<eventId>",
      "outcome": {"kind": "result", "value": "allowed-once"}
    }
  }
}
```

实测结果：

| 场景 | 结果 |
|---|---|
| allow | `approval/decided {outcome:"allowed-once"}` → `job/registered` → `job/settled` → `tool/result "P0_APPROVAL_OK"` → `turn/end completed` |
| reject | `approval/decided {outcome:"rejected"}` → `tool/result "Error: the user rejected …"` → `turn/end completed`，命令未执行 |
| 双 answer 竞态 | A、B 收到同一 `eventId`；A 答 `allowed-once`；B 收到 `{"type":"cancel","eventId":"…"}`；A 也收到 cancel 用于清理 |
| 唯一 answer 客户端断开 | pending 不取消、不自动允许；turn 保持 `running`；新 answer 客户端会再次收到同一 `eventId` |
| `interactions=none` | `$events` open 返回 `gateway/interactions-forbidden`；`session/follow` 仍可用 |
| `none` 客户端触发审批 | 90s 内没有 `turn/end`；审批停在 `approval/asked`，直到后来的 answer 客户端处理 |

**结论**：审批的“允许/拒绝/竞态”通过；“无 answerer 时 fail closed”**失败**。这是 P0 最重要的阻塞项。

### P0-6 断线、客户端退出、Host 重启

三类场景分开测：

1. **只断 socket**
   - [x] 关闭 WebSocket 后，旧 Cookie 发 HTTP → 401
   - [x] 同一 token 重新 `/connect` → 新 Cookie、新 `clientId`
   - [x] 新 Cookie 可以继续 `session/list` / `session/follow`

2. **客户端进程退出（Host 任务继续）**
   - [x] 启动 `sleep 20; echo P0_SURVIVED`，看到 `tool/call` 后关闭客户端
   - [x] 25 秒后重连，历史里有 `job/settled`、`tool/result "P0_SURVIVED"`、`turn/end completed`

3. **Host 重启**
   - [x] 旧 token `/connect` → 401
   - [x] 旧 Cookie `session/list` → 401
   - [x] 新 token 正常连接
   - [x] 之前的 session 仍在：`formatStatus="current"`、`agentAvailable=false`、`running=false`
   - [x] 对 `agentAvailable=false` 的旧 Session 发 prompt，能重新拉起 Agent，返回 `P0_RESUMED`

**结论**：通过。客户端和 Host 的重启语义已经明确；错误处理需要把 401 映射成“启动 URL 已失效，请重启 Host 并粘贴新 URL”。

### P0-7 非交互模式

- [x] `interactions=none` 连接
- [x] `$events` 被拒绝
- [x] `session/follow` 仍可用
- [x] `session/prompt` 仍可用
- [ ] 没有 answerer 时审批 fail closed
- [!] 有另一个 answer 客户端时，审批会被它接走

实测：`none` 客户端发一个需要 escalation 的 prompt，Host 记录 `approval/asked` 后停住；90 秒没有 `approval/decided`，也没有 `turn/end`。后来单独开一个 `answer` 客户端，立刻收到同一个 pending `eventId`，拒绝后才结束。

**结论**：`-p` 目前 **No-Go**。不能假设“没有 UI 就会自动拒绝”。

### P0-8 版本与 Host 插件判定

- [x] `$events.ready`：只有 `{ clientId, host: { home } }`
- [x] `/connect` 响应头：`cache-control: no-store`、`location`、`referrer-policy`、`set-cookie`；没有版本
- [x] 无 Cookie `GET /` → 401；看不到静态版本
- [x] 未知 API → 404
- [x] `headless` profile 没有 `client-connection` / `session-controller` / `api-remotes`

**结论**：没有受支持的版本握手。三个选项：

| 选项 | 评价 |
|---|---|
| A. 最小 Host 插件，上报版本 + capability + 审批策略 | **生产推荐**；同时能解决 fail-closed/超时 |
| B. 纯行为探测（试调用 + 错误分类） | 原型可用；无法区分“版本旧”与“配置缺失” |
| C. 静态资源 hash 弱识别 | 不作为唯一依据 |

**P0 决定**：原型可以先走 B；生产必须 A。原先“插件 optional”的说法不成立。

## 7. 决策点

1. **`-p` 的审批策略**
   - 方案 1：Host 插件提供 `approval` 超时/默认拒绝；
   - 方案 2：CLI 以 `answer` 连接，自己实现 `--approval=reject|allow-once|ask`；
   - 方案 3：`-p` 遇到审批直接返回明确错误并取消 turn。
   - 无论哪种，都不能依赖“没有 answerer 就自动拒绝”。

2. **P2 的客户端形态**
   - 推荐：`api-gateway/client` + `session-controller/remote` + 自建 store；
   - 不推荐：在 Node 里 shim `window` 去跑 `session-controller/client`（它会继续依赖浏览器模块加载器）。

3. **版本/能力握手**
   - 生产加最小 Host 插件；
   - 原型用行为探测，并在错误信息里明确“无法确定 Host 版本”。

4. **token 保存**
   - 默认只存内存；
   - 可选 OS keychain，但要标注“Host 重启即失效”；
   - 绝不写入仓库、日志、shell history 或最终回复。

5. **审批 UI 的重连**
   - 新 `answer` 客户端连上后会收到 pending `eventId`，TUI 必须能重新渲染；
   - 本地超时只能“停止等待”，不能假装 Host 已经拒绝；要发 `rejected` 才算真正关闭。

6. **多 answer 客户端**
   - 依赖 Host 的 first-result-wins；
   - 所有客户端（包括答完的那个）都会收到 `cancel`，按幂等处理。
