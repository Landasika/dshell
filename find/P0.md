# P0 — 连接与 API 可行性执行计划

> 本文是 [`docs/development/00-feasibility.md`](../docs/development/00-feasibility.md) 的执行版，暂存在 `find/`，**不回写 `docs/development/`**。
> 所有“已确认”项都来自 2026-10-23 对 DSH `master` / `0.2.1-rc.2` 的源码与文档核对，仍须在 PoC 中复验。

## 1. 目标

在写 CLI/TUI 之前，用一个最小 Node.js 进程证明：

> 独立 Node 客户端 + 已运行的 DSH Host，可以构成完整、可恢复的双进程 Agent 体验。

具体就是这条闭环：

```text
读启动 URL → 交换 token → 建立 Connection
  → 列 Workspace / Session → 建 Session → 发 Prompt
  → 收流式事件 → 处理审批 → 断开 → 重连 → 历史一致
```

P0 是 **Go/No-Go 门槛**，不是演示 Demo。计划里明确的硬规则：

> **如果审批/授权不可用，不进入 P4 UI 开发。**

## 2. 范围

### 做

- 非浏览器 Node 客户端的认证、`interactions=answer|none`、Cookie 生命周期
- Workspace / Session 列表、创建、打开
- Prompt、Queue、Cancel、流式事件、历史分页
- Approval / Ask User 的接收、应答、失效
- 客户端退出、socket 断线、dshell 进程重启、Host 重启
- 判定“最小 Host 插件是否必要”

### 不做

- TUI、终端渲染、快捷键
- npm 打包与发布
- 完整的 `DshellBackend` 抽象与上层业务
- 多版本兼容矩阵（P6）
- 多 Workspace 的完整产品 CLI（P3）

## 3. 已确认的 Host 事实

这些事实决定了 P0 必须怎么测，不能按“浏览器会自动重连”的直觉写。

| # | 事实 | 影响 |
|---|---|---|
| 1 | `@deepseek-ai/dsh-client-connection/client` 有 `node` 条件导出，Node 下加载 `lib/client.node.js` | Node 客户端可行，有官方 Node 测试路径 |
| 2 | API 客户端通过 `GET /connect?token=...&interactions=answer\|none` 换取 Cookie | token 是入口，不是可自动发现的东西 |
| 3 | `/connect` 发布的是 **owner** principal；Remote access 的角色策略只约束非 owner | 连上 dshell = Host owner 权限，凭据必须按敏感信息处理 |
| 4 | launch token 只存在 Host 进程内存，启动时打印在 `dsh web:` URL；没有持久化接口 | dshell 必须让用户提供带 token 的 URL，或自己保存 token |
| 5 | API Peer 与生命周期 socket 绑定：socket 关闭后 Peer 删除，旧 Cookie 失效，须重新 `/connect` | 不能只依赖 Connection 自带 recovery；要单独实现 re-auth |
| 6 | 目前开箱即用、同时挂 Connection + session-controller + api-remotes 的是 `dsh --profile web`；`headless` 不挂 Host/HTTP | P0 的 Host 基线是 web profile，不是任意 DSH 进程 |
| 7 | `$events` 的 `ready` 帧只有 `{ clientId, host: { home } }`，没有 Host 版本；没有 version RPC | “版本判定/不支持版本诊断”目前没有数据源，需要拍板 |
| 8 | Gateway 把 `approval/request` 转发给所有 `answer` peer，第一个 result 生效，其余收到 cancel | 多客户端审批场景可测；但“最后一个 answer 客户端断开”要单独验证 |
| 9 | DSH 的 Node 要求是 `^22.19.0 \|\| >=24.0.0` | 锁定 engines，CI 按此验证 |

- [authenticated Node client test](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/api/gateway/tests/authenticated-node.client.spec.ts)

## 4. 环境基线

PoC 阶段先固定一套环境，避免“今天能跑、明天不能跑”。

```text
DSH:   0.2.1-rc.2（npm dist-tag: next；不要用 latest）
Node:  ^22.19.0 || >=24.0.0
pnpm:  11.x
Host:  dsh --profile web --no-open --port 3080
Client: 独立的 Node ESM 进程（poc/）
```

安装时精确 pin 版本：

```bash
pnpm add @deepseek-ai/dsh-client-connection@0.2.1-rc.2
pnpm add @deepseek-ai/dsh-api-gateway@0.2.1-rc.2
pnpm add @deepseek-ai/dsh-api-session-controller@0.2.1-rc.2
pnpm add @deepseek-ai/dsh-api-workspace-controller@0.2.1-rc.2
pnpm add @deepseek-ai/dsh-client-file-upload@0.2.1-rc.2
pnpm add @deepseek-ai/dsh-typert-registry@0.2.1-rc.2
```

先在 `poc/` 里验证，不急着建正式 `src/` 目录。

## 5. 最小架构

```text
┌──────────────────────────────┐
│ dshell P0 进程（Node ESM）    │
│                              │
│  token/URL 解析              │
│  Cookie jar                  │
│  installConnection()         │
│    ├─ HTTP fetch             │
│    └─ WebSocket /api/remote.mux
│  ctx.remote（gateway client）│
│  ctx.sessions（session client）│
│  approval/request listener   │
└──────────────┬───────────────┘
               │ HTTP + WS（owner Cookie）
┌──────────────▼───────────────┐
│ DSH Host（dsh --profile web）│
│  Connection / Gateway        │
│  session-controller          │
│  workspace-controller        │
│  Agent / 工具 / 审批          │
└──────────────────────────────┘
```

原则：

- **不要**先引入整个 `@deepseek-ai/dsh-api-remotes`（Web 端组装，`dsh.client.platform: web`）。P0 只挂需要的 namespace：`session`、`workspace`、`fileUpload`、`subagents`。
- **不要**自己实现 Agent Loop、Session 持久化、工具或策略；这些全在 Host。
- `session-controller/client` 是 React-free 的 Client Model，但它 `inject` 了 `fileUpload`。Node 侧要么提供最小 `fileUpload` 服务，要么只用 `Uint8Array` 路径（官方实现只有这条路径不依赖 Worker/DOM）。

## 6. 实验步骤

每一步都要留下“命令 / 输入 / 输出 / 结论”，最后汇总进 `find/p0-report.md`。

### P0-0 固定环境

- [ ] 记录 `dsh --version`、Node 版本、OS、DSH 安装方式
- [ ] 记录 Host 启动命令、端口、bind 地址、是否 TLS
- [ ] 记录 npm 包精确版本（`pnpm list --depth 0`）
- [ ] 把 Host 启动 URL 原样保存到本地临时文件（含 token，**不要提交**）

**通过标准**：任何人按记录能重启同一套环境。

### P0-1 token → `/connect` → `$events`

- [ ] 从启动 URL 解析 `token`
- [ ] 手动处理 302，请求 `GET /connect?token=<token>&interactions=answer`
- [ ] 保存 `Set-Cookie`（注意 cookie 名是按 authority 哈希的）
- [ ] 用同一 Cookie 发一个 HTTP RPC
- [ ] 用同一 Cookie 打开 `/api/remote.mux`，订阅 `$events`
- [ ] 收到 `{ type: 'ready', clientId, host: { home } }`

**失败信号**：401（token/cookie 错）、403（Host/Origin 信任失败）、409（同一 API socket 重复附着）。

**记录**：cookie 名、过期时间、`ready` 原始帧、Host 的 `home`。

### P0-2 挂最小 Remote 命名空间

- [ ] `@deepseek-ai/dsh-typert-registry` + `@deepseek-ai/dsh-api-gateway/client`
- [ ] 挂 `session`、`workspace`、`fileUpload`、`subagents` 的 Remote 贡献
- [ ] 调 `session.list` 和 `workspace.list`
- [ ] 确认返回结构与 `types` 导出一致

**通过标准**：不依赖 DOM/React，能在纯 Node 里拿到列表。

**注意**：如果 `session-controller/client` 因为 `fileUpload` 注入失败，先写一个最小 Node `fileUpload` 实现（只支持 `Uint8Array`），不要为了跑通去引浏览器 Worker。

### P0-3 建会话 + Prompt + 流式

- [ ] `session.create` 建一个新 Session（记录 workspaceId、cwd）
- [ ] `session.prompt` 发送一条简单文本
- [ ] `session.follow` 接收流式事件
- [ ] 确认能看到：用户消息、assistant 增量/完成、工具调用/结果、turn 结束
- [ ] 记录事件顺序、`seq`、`turn/start`/`turn/end` 边界

**通过标准**：最终答案完整，事件没有丢序/重复。

### P0-4 历史与分页

- [ ] `session.page` 拉一页历史
- [ ] `loadOlder` 再拉一页
- [ ] 断开后重新 `follow`，基线 + 增量一致
- [ ] 对比断开前/后的 transcript、最后一条 assistant message

**通过标准**：历史不丢、不重、顺序稳定。

### P0-5 审批与多客户端

- [ ] 触发一个需要审批的工具动作（按 Host 的 approval policy）
- [ ] dshell 收到 `approval/request`，包含 agent/tool/callId/reason
- [ ] 提交 `allowed-once`，工具继续
- [ ] 再触发一次，提交 `rejected`，工具失败关闭
- [ ] 两个 `answer` 客户端同时收到同一请求；一个先答，另一个收到 cancel/失效
- [ ] 只开 `interactions=none` 的客户端，确认收不到审批，Host fail closed

**通过标准**：不会重复有效处理；不会自动放行；过期/断线请求不误解。

### P0-6 断线、进程重启、Host 重启

分三种，不要混在一起：

1. **只断 socket**
   - [ ] 关闭 WebSocket，观察 Host 删除 Peer
   - [ ] 用旧 Cookie 发 HTTP，确认 401
   - [ ] 用同一 token 重新 `/connect`，拿到新 Cookie，恢复 `$events`
2. **杀掉 dshell 进程**
   - [ ] Host 上的任务继续跑（用长任务验证）
   - [ ] 重启 dshell，用保存的 token 重新 `/connect`
   - [ ] 打开同一 Session，历史与运行状态一致
3. **重启 Host**
   - [ ] 旧 token 失效
   - [ ] dshell 报错可理解，并提示重新获取启动 URL

**通过标准**：三种场景的预期行为写进 `compatibility-risks.md`，错误信息不误导。

### P0-7 非交互模式

- [ ] `interactions=none` 连接
- [ ] 发 prompt，触发一个需要审批的动作
- [ ] 确认没有 answerer 时审批 fail closed，任务不会静默通过
- [ ] 记录“如果同一 Host 还有 Web UI/另一个 answer 客户端，审批可能被它接走”的事实

**通过标准**：`-p` 的失败是明确的，不是“看起来成功了”。

### P0-8 版本与 Host 插件判定

- [ ] 尝试从 `$events`、HTTP 头、静态资源、任何 RPC 获取 Host 版本
- [ ] 如果拿不到，评估三个选项：
  - A. 加最小 Host 插件，上报版本 + capability
  - B. 只做行为探测（尝试调用 + 错误分类），降低兼容承诺
  - C. 静态资源 hash 弱识别（不推荐作为唯一依据）
- [ ] 给出 P0 结论：插件是 optional 还是 required

**通过标准**：P2/P6 不需要猜“Host 是什么版本”。

## 9. 风险与决策点

| 风险 | 影响 | P0 决策 |
|---|---|---|
| token 只能从启动 URL 获取 | 用户体验差；Host 重启即失效 | 存内存 / 存 keychain / 每次粘贴，三选一 |
| API Peer 与 socket 绑定 | 自带 recovery 不适用 | 自己实现 re-`/connect` 循环 |
| `session` client 依赖 `fileUpload` | 纯 Node 挂载可能失败 | 最小 Node shim 或只用 `Uint8Array` |
| 只有 web profile 提供完整 API | 用户必须先开 Web Host | 写清 Host 前置条件；评估最小 host bundle |
| 没有版本握手 | P6 无法给“不支持版本”诊断 | 加插件 / 行为探测 / 降低承诺 |
| 多 answer 客户端审批竞态 | 可能重复处理 | 依赖 Host 的 first-result-wins，不本地抢答 |
| 最后一个 answer 客户端断开 | pending 可能悬挂 | 实测并定义超时/重连策略 |
| 浏览器 only 模块 | Node 加载失败 | P0-2 逐包验证，记录替代方案 |

## 10. 工作量

1 人约 **3–5 个工作日**：

- 第 1 天：环境 + `/connect` + `$events`
- 第 2 天：挂 Remote + 列表 + 建 Session
- 第 3 天：Prompt + 流式 + 历史
- 第 4 天：审批 + 双客户端
- 第 5 天：三种重连 + 报告 + Go/No-Go

认证和重连通常占一半时间，别低估。
